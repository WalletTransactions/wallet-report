# Design

## Context

- `handle_operations` (`src/reports.cpp`) проверяет `from`/`to`, `limit`,
  пару курсора и зовёт `reports_repo::operations_for_period`. Тот выбирает
  один из двух текстов SQL: без `$6/$7` для первой страницы и с ними для
  следующих, потому что `db::Database::exec()` не передаёт SQL NULL
  (`db.hpp`). Пагинация «с подглядыванием» берёт `limit + 1` строк.
- Функции в базе принадлежат wallet-api. Новая сигнатура
  `f_operations_for_period(…, p_category_uuids uuid[], p_wallet_uuids uuid[],
  p_kind text, p_q text)` (все новые с `DEFAULT NULL`) и
  `f_operations_total(p_ledger_id, p_from, p_to, p_eq_currency, <те же 4 фильтра>)
  → (total_eq, incomplete, matched)` описаны в
  `wallet-api/openspec/changes/add-operations-filter-functions/design.md`
  (D1–D4), там же правило знака.
- Поведение — `specs/operations-list/spec.md` этого change.

## Goals / Non-Goals

**Goals:**
- Любые сочетания фильтров без SQL NULL и без комбинаторного числа текстов
  запроса.
- Ошибки ввода — 400 с дословными текстами до обращения к базе. Ошибка
  приведения `::uuid[]` в Postgres не должна превращаться в 500.
- Ответ без фильтров побайтно тот же, что сейчас, и без второго запроса.

**Non-Goals:**
- Переход веба и бота на серверные фильтры. Они продолжают фильтровать
  загруженные страницы, это отдельные изменения.
- Сортировка, отличная от «дата по убыванию», и поиск по имени
  категории/кошелька (для этого есть `/accounts` и `category_uuid`).

## Decisions

### D1. Именованная нотация вместо вариантов текста запроса

`operations_for_period` получает структуру `OperationsFilter
{category_uuids, wallet_uuids, kind, q}` (пустые = не задано) и собирает текст
вызова: позиционные `$1..$5` (ledger, from, to, eq, limit+1), затем по имени
только заданные параметры (`p_cursor_date => $n, p_cursor_uuid => $n+1`,
`p_category_uuids => $n::uuid[]`, …) с последовательной нумерацией. Два
нынешних текста становятся частным случаем этой сборки. Значения по-прежнему
идут параметрами `$n`, а не подстановкой в текст, так что инъекции нет: из
фиксированного набора имён собирается только сам текст.

Альтернатива — пустой массив и пустая строка как «нет фильтра» с
позиционной передачей всех 11 параметров — отклонена: курсор первой страницы
всё равно пришлось бы слать NULL, а `'{}'` означало бы «ни одной категории».

### D2. Проверка ввода в `handle_operations`

- Списки: `split(',')`, каждый элемент по шаблону uuid
  `^[0-9a-fA-F]{8}-([0-9a-fA-F]{4}-){3}[0-9a-fA-F]{12}$`, пустой элемент —
  ошибка, больше 50 — ошибка. Дубли допустимы. Наружу передаётся литерал
  массива `{u1,u2}`.
- `kind` — одно из трёх значений.
- `q` — длина в кодовых точках UTF-8 (подсчёт байтов, не являющихся
  продолжением `10xxxxxx`), не больше 100. Битый UTF-8 отклоняется с тем же
  текстом про длину.
- Порядок проверок: `from`/`to` → `limit` → курсор → фильтры, чтобы
  существующие сценарии отвечали прежними текстами.

### D3. Итог — второй запрос только при фильтрах

Если хоть один фильтр задан и у пользователя есть леджер, после страницы
выполняется `SELECT total_eq, incomplete, matched FROM f_operations_total(...)`
на том же соединении из пула, собранный так же, как в D1 (без курса и лимита).
В ответ добавляются `total_eq` (строка `numeric` из базы как есть), `total_incomplete`,
`total_count`. Нет леджера — `"0"`, `false`, `0` без запроса.
Один запрос с оконной функцией (`sum() OVER ()`) отклонён: окно считает
итог только по строкам до `LIMIT`, а нужен итог за весь период.

`total_count` добавлен сверх исходного контракта: `wallet-mcp` нужно
сказать «нашлось 40, показаны 10», а `matched` функция считает бесплатно.

### D4. Контракт и документация

`openapi.yaml`: четыре параметра у `reportOperations` с описанием
семантики (И/ИЛИ, сторона проводки, `ё` = `е`, лимиты) и ответом 400;
`OperationsReport` получает необязательные `total_eq`, `total_incomplete`,
`total_count` с пометкой «есть только при фильтрах» и правилом знака.
Описание ручки больше не говорит «без фильтров на сервере».
`README.md`: строка `/operations` в таблице эндпоинтов. Комментарии в
`reports.cpp`/`reports_repo.hpp` про «фильтров на сервере нет» исправляются.

### D5. Тесты

Интеграционные, в `tests_integration/test_reports.cpp` по образцу
существующих `operations_for_period_*`: засев через `sync_repo`, вызов
`reports_repo` напрямую. Проверки 400 (D2) — юнитом не покрыть, юнит-тестов у
сервиса нет. Они проверяются через curl на живом стеке, а логика разбора
выносится в чистую функцию, если это понадобится для теста.

## Risks / Trade-offs

- [wallet-report выкатили раньше миграции wallet-api] → именованные параметры
  неизвестны, и запросы с фильтрами отвечают 500. Без фильтров текст вызова тот
  же, что сейчас, поэтому лента работает. Порядок выката «миграции → сервис»
  уже закреплён в контурах.
- [Итог и страница считаются двумя запросами без общей транзакции] → между
  ними может прийти синк, и итог разойдётся со страницей на одну операцию. Для
  отчёта это допустимо, ровно так же устроены соседние страницы курсора.
- [Условие фильтра в двух SQL-функциях разойдётся] → тест согласованности:
  `total_count` равен числу строк по всем страницам, `total_eq` равен сумме
  по ним с правилом знака.
- [Нагрузка от `q` на долгом периоде] → замер в нагрузочном наборе
  (`loadtest/`): сценарий ленты за год с `q`.

## Migration Plan

1. Миграция wallet-api `add-operations-filter-functions` в контуре.
2. Выкат wallet-report. До шага 2 старый wallet-report продолжает работать на
   новой сигнатуре через позиционный вызов.
3. Откат wallet-report безопасен в любой момент. Откат миграции — только после
   отката wallet-report.
