# Proposal

## Why

Новый MCP-сервер `wallet-mcp` должен отвечать на вопросы вида «сколько ушло на
такси» или «покажи траты на няню из кошелька Тинькофф». Сейчас `/operations`
(`reportOperations`) отдаёт только ленту периода страницами по 1000, без
фильтров. Фильтровать на клиенте можно лишь листая все страницы, а итог по
найденному пришлось бы складывать модели, хотя по правилу проекта суммы
считает SQL, а не LLM. Серверные фильтры с итогом пригодятся и вебу, и боту
(`/last`): сейчас они фильтруют уже загруженные страницы.

## What Changes

- `/operations` принимает необязательные фильтры, все применяются вместе (И):
  - `category_uuid` — одна или несколько категорий (ИЛИ внутри списка);
  - `wallet_uuid` — один или несколько кошельков: операция подходит, если
    кошелёк участвует в ней с любой стороны, в том числе в прямом переводе;
  - `kind` — `expense` / `income` / `transfer`;
  - `q` — подстрока комментария без учёта регистра, `ё` = `е` (тот же принцип,
    что у сопоставления имён в боте).
- Фильтры применяются **до** лимита страницы, поэтому курсорная пагинация,
  `has_more` и правило «каждая операция ровно один раз» продолжают работать на
  отфильтрованном наборе.
- Если передан хотя бы один фильтр, ответ содержит `total_eq` — сумму
  `amount_eq` **всех** подходящих операций периода, не только страницы, — и
  `total_incomplete`, если у части из них нет курса к `eq_currency`, и
  `total_count` — число подходящих операций. Без `kind` итог — сальдо (доходы
  минус расходы), с `kind` — сумма операций этого типа. Без фильтров
  ответ прежний, `total_eq` нет, а расход на дополнительный запрос не тратится.
- Требование «Поиск и фильтрация … на сервере не выполняются» заменяется
  описанием фильтров. Без фильтров поведение не меняется, поэтому изменение не
  ломает текущих клиентов.

### Modified Capabilities
- `operations-list`: серверные фильтры по категории, кошельку, типу и тексту
  комментария до пагинации; итог `total_eq` / `total_incomplete` по всем
  подходящим операциям периода.

## Impact

- **wallet-api (обязательная зависимость, отдельный change):** новая миграция.
  `f_operations_for_period` делает `LIMIT` внутри себя, поэтому фильтр поверх её
  результата сломал бы пагинацию. Нужны параметры фильтра в функции, или новая
  функция, и функция итога по тем же условиям, а также зеркала в
  `schema/function/`. `db::Database::exec()` не умеет передавать SQL NULL, поэтому
  «нет фильтра» должно кодироваться значением, например пустым массивом или
  пустой строкой, — это решение для design.
- **wallet-report:** `reports_repo` (вызов с фильтрами, второй запрос итога),
  разбор и проверка параметров (некорректный uuid или `kind` → 400),
  `openapi.yaml` (`reportOperations`), таблица эндпоинтов в `README.md`,
  интеграционные тесты в `tests_integration/` (фильтры с пагинацией, итог,
  кириллица и `ё` в `q`).
- **wallet-gateway:** без правок, путь остаётся `/api/reports/operations`.
- **Потребители:** `wallet-mcp` (инструмент `search_operations`). Веб и бот
  могут перейти на серверные фильтры позже, по желанию.
- **Производительность:** фильтр `q` — последовательный просмотр операций периода
  в одном леджере. Для личных объёмов индекс не нужен, это стоит проверить на
  нагрузочном наборе `loadtest/`.
